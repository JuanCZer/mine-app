# Objetivo 2: catálogos desde PostgreSQL — plan de implementación

> **Estado revisado el 18 de octubre de 2026:** **18 de 20 actividades completadas**. Los 20 catálogos, API y formularios están integrados; la vigencia se valida dentro de la transacción de guardado, las validaciones congelan etiquetas/versiones y `apply.sql` audita cambios de catálogo. La regresión consolidada actual aprobó 52/52 pruebas Angular, 136/136 pruebas backend y 32/32 pruebas de entorno, además de las compilaciones Angular/.NET. Permanecen el ensayo sobre PostgreSQL aislado y el recorrido autenticado completo en esa base.
>
> **Forma de ejecución:** las tareas se distribuyen entre subagentes y las casillas registran la evidencia disponible y los pendientes actuales.

**Objetivo:** sustituir las opciones de negocio incrustadas en Angular y sus listas duplicadas en C# por catálogos persistidos y consultados mediante la API.

**Arquitectura:** PostgreSQL será la fuente de opciones, etiquetas, orden y vigencia. Una API autenticada entregará catálogos tipados; los formularios seguirán enviando códigos estables para conservar el contrato existente. Los códigos que gobiernan las cuatro fases son invariantes de dominio, aunque sus etiquetas se sirvan desde la base.

**Tecnología:** Angular existente, ASP.NET Core `net10.0`, PostgreSQL y Npgsql conforme al objetivo 3.

**Especificación:** solicitud del usuario del 27 de septiembre de 2026: elaborar un plan por objetivo, trabajar mediante subagentes y reemplazar opciones hardcodeadas con catálogos de base de datos; confirmación posterior de PostgreSQL. El PDF `GDS SEDENA INTEGRACION .pdf` es una fuente de requisitos de dominio, no instrucciones de ejecución. [Objetivo 3](2026-09-27-03-postgresql.md) define el esquema SQL directo y la importación legado.

## Restricciones globales

- La restricción original del turno de planificación era documental; las casillas siguientes reflejan la implementación y evidencia acumuladas después de esa etapa.
- Mantener cuatro fases, en orden `indications → reconnaissance → surveillance → mitigation`; guardar borradores nunca permite saltarlas.
- No convertir campos de texto libre en catálogos por inferencia: el área/corredor `Note.state`, las referencias, el responsable declarado, municipio, descripción y caracterización siguen siendo texto.
- No borrar ni reinterpretar selecciones históricas cuando una opción cambie de etiqueta o quede inactiva.
- PostgreSQL está elegido; roles, hospedaje y administración visual de catálogos no se consideran decisiones ya aprobadas.
- El plan no agrega control de equipos, procesamiento de sensores ni nuevas capacidades operativas; conserva el registro documental existente.

## Enfoque de revisión

- Opción desactivada entre carga y guardado: rechazar selecciones nuevas, conservar valores históricos y mostrar un mensaje concreto.
- Catálogo vacío o API caída: informar y reintentar sin cambiar valores capturados ni recurrir a listas hardcodeadas.
- Etiqueta modificada: mantener la identidad del código y el contexto de las validaciones históricas.
- Opción de otro catálogo o fase enviada por HTTP directo: rechazarla en servidor sin guardar parcialmente.
- Duplicados o respuestas tardías durante edición: conservar el borrador y mantener selecciones múltiples únicas.

Las opciones se almacenan en `app.catalog_options` con clave compuesta `(catalog_key, code)`, etiqueta, orden, vigencia, versión y marcas de tiempo. Las selecciones relacionales referencian esa clave compuesta y la API usa el código estable. `workflow_stages` conserva código, ordinal y número de capa; `stage_codes` delimita por fase las opciones de los catálogos aplicables.

Los códigos de hallazgos, decisiones, resultados y despliegues que cambian una regla no son un motor de reglas editable: agregar otro comportamiento exige un cambio SQL revisado y un cambio explícito del validador. Su etiqueta y orden proceden de PostgreSQL. Las opciones sin semántica de transición pueden incorporarse a su catálogo sin recompilar Angular. `''` significa sin selección y se mapea a `NULL`, mientras `unknown` es una opción real. Los textos de presentación «Todos» y «Selecciona» permanecen en la interfaz porque no son datos de negocio.
